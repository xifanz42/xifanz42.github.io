从 0 到 1 构建面向 Web3 合规服务场景的 B2B 销售情报 SaaS，打通数据清洗、公司检索、试用线索推荐、用户行为追踪与多租户权限，并推进到真实付费验证。
角色 独立开发 —— 产品定义、数据建模、前后端、部署运维全栈负责
时间线 2025-09 → 2026-04（核心开发集中在 2025-11 → 2026-01）
形态演进 Streamlit 原型（2025-11） → Next.js 正式应用（2025-11 → 2026-01）
技术栈 Next.js / React / TypeScript / Tailwind CSS / shadcn-ui / Supabase (PostgreSQL) / Row Level Security / SQL RPC / Python / Cloudflare Pages
状态 已停止（Retired）—— 销售侧无渠道，商业决策 pivot

产品演示
#

演示视频占位。建议录制路径：公司检索与多维筛选 → 公司详情（合规状态 / 联系人 / 关联方）→ 收藏 → onboarding 输入 ICP → 试用线索分批释放。

一、问题为什么难
#

目标用户是 Web3 合规咨询、托管、审计、支付与链上安全服务商的 BD 和销售团队。

他们要回答的不是"有哪些公司"，而是"哪些公司现在有合规需求、谁是关键决策人、这家公司跟谁有关联、风险信号在哪"。通用 CRM 和人工名单覆盖不了这类结构化信号 —— 牌照状态、关联主体、股权层级、风险事件，这些字段不存在于任何通用数据源里。

第一个决策：把"要采什么数据"变成可执行矩阵
#

我没有按数据源组织采集计划，而是按行业场景 × 司法辖区组织：7 个一级行业 × 18 个二级场景 × 5 个重点辖区（新加坡、中国大陆、中国香港、迪拜、美国）= 90 个覆盖单元，然后按辖区差异化定优先级：

  • 中国香港 / 新加坡 / 美国 —— 接近全量覆盖，Web3 与金融服务场景基本都做
  • 中国大陆 —— 偏向传统金融、投资机构、做市与 OTC、支付、跨境电商；主动弱化加密原生场景（监管可行性优先于市场容量）
  • 迪拜 —— 覆盖金融、OTC、支付、托管、区块链开发；GameFi / NFT / 数据平台等应用层降优先级

它的价值不在于"规划得很细"，而在于把"我们要不要做这个市场"从一个拍脑袋问题，变成了可以按单元排序、按 ROI 取舍的清单。90 个单元里我最终只深做了其中一小部分 —— 而正是这个矩阵让我看清楚了这一点。

决策 1：权限下沉到数据库（RLS），而不是应用层鉴权
#

备选 A. Postgres RLS 策略 ｜ B. 应用层 service 层统一拦截 ｜ C. 每个 query 手写过滤条件
选择 A
理由 单人开发，数据入口分散在 24 个 RPC 函数和前端直连查询之间。任何依赖"记得加 where 条件"的方案迟早会漏一次。把权限写进 schema，让"忘记鉴权"在物理上不可能发生。
代价 调试从 TypeScript 转移到 SQL —— policy 递归、查询计划劣化都更难排查。51 条策略的维护负担是真实的。
复盘 policy 应该按「角色 × 资源」模板化生成，而不是逐表手写。后期新增表时我确实漏过一次。

决策 2：规则化 ICP 排序，不做机器排序
#

备选 A. 规则加权排序 ｜ B. 学习排序（Learning to Rank）
选择 A
理由 清洗后可用公司记录只有 36 条，用户行为样本更少。这个量级上任何模型的方差都远大于信号，而且根本没有 ground truth 可训。上模型是自欺欺人。
代价 排序质量的上限被规则写死，无法随数据积累自动变好。
复盘 “不做 ML"这个决定是对的，但配套漏了一件事 —— 我没有把人工判断的排序结果存下来。如果当时把用户对每条线索的采纳 / 拒绝结构化记录成 eval set，即使不上模型，也能量化规则本身的好坏。这是我今天做 AI 系统时最先补的一环。

决策 3：SQL migration 作为 schema 的唯一来源，不用 ORM
#

备选 A. 手写 SQL migration ｜ B. ORM（Prisma / Drizzle）schema-first
选择 A
理由 这个项目里重的东西 —— RLS 策略、RPC 函数、视图、触发器 —— 全都在 ORM 的抽象盲区。用 ORM 反而要维护两套：一份 ORM schema，一份 raw SQL escape hatch。
代价 类型安全得自己补（Supabase CLI 生成 TypeScript 类型），重构时没有 ORM 的自动迁移提示。
复盘 正确选择。53 个 migration 一路改下来，schema 演进的可读性远好于我见过的多数 ORM 项目。

三、Prototype：那段跑通过、但没进产品的 LLM 层
#

本节描述的功能存在于 2025-11 的 Streamlit 原型中，从未进入 Next.js 正式产品。

我把它写出来，是因为它解释了后面「如果重做我会怎么做」的判断依据。LeadX 不是一个 AI 产品。

Streamlit 原型里我实现过一个 ProductionLLMService，接 OpenAI 兼容接口（SiliconFlow，model inclusionAI/Ling-flash-2.0），支撑两个功能：基于公司档案的问答助手、外联邮件优化。它不只是"调一下 API”：

  • Prompt 模板化 —— PromptTemplates 与 LLMConfig 集中管理，build_chat_system_prompt() 按用户画像和行业上下文动态拼装
  • 多轮对话持久化 —— 对话历史落 Postgres，_get_conversation_history() 带 limit 裁剪，而不是把全量历史塞回 prompt
  • 响应缓存 —— _get_cache_key() 对 query + context 做 hash，命中直接返回。纯成本考虑
  • 可观测性 —— _log_llm_usage() 记录 input/output tokens、成本、耗时、action_type，另有 get_user_cost_summary() 按用户聚合
  • 降级兜底 —— LLM_API_KEY 缺失时进入 fallback 模式返回 get_fallback_response()，不让功能直接挂掉

另外，数据库 schema 里我预留了 embedding_vector extensions.vector(1536) 列。但它和向量检索一样从未落地 —— 没有 ivfflat / hnsw 索引，没有 embedding 生成代码，没有检索代码。列是空的。

为什么没进产品： 不是判断 AI 没有价值，是 scope。正式版的优先级全给了核心数据表、权限体系和检索稳定性，LLM 排期靠后被挤掉。等它重新排上日程时，项目已经因为销售侧原因 pivot。

这是我这次最实在的一个教训：如果 AI 能力不在第一版的核心价值路径上，它就会被无限期推迟。

五、结果与复盘
#

商业化结果：1 个付费用户，1 个试用用户。 项目随后 pivot。

pivot 的真实原因不是技术，是渠道。 工程侧的闭环跑通了，但我始终没能建立起可重复的销售渠道 —— 没有稳定的触达路径，就没有足够的销售漏斗去验证定价和 PMF。工程交付能力从来不是这个项目的瓶颈。

我错在哪
#

  1. 把"数据质量"当成产品的全部，低估了"让人知道你存在"的难度。 在 B2B 数据产品里，分发往往比数据更难。
  2. 覆盖矩阵设计了 90 个单元，实际只深做了很小一部分。 数据供给深度不足，导致 Demo 的说服力够，但留存不够。
  3. 没有在早期把用户判断存成可量化的 eval set。 到最后"推荐到底好不好"仍然是主观问题，无法迭代。

今天我会怎么重建
#

  • 规则化 ICP 匹配 → 语义检索 + 结构化 filter + rerank 的两阶段召回
  • 主观的"推荐好不好" → 把用户采纳 / 拒绝行为直接建成 eval set，上线当天就有可量化基线
  • 人找数据 → Agent 主动挖掘：给定 ICP 描述，自动拆解成检索子任务、调工具取数、交叉验证后输出带证据链的线索卡片
  • 成本与可观测性沿用原型那套 —— 响应缓存、token 与成本埋点、降级兜底。这部分设计我今天会原样照搬
这个项目的价值不在"做成了一个产品"，而在于完整走了一遍：产品假设 → 数据覆盖规划 → 工程实现 → 上线 → 销售验证 → PMF 复盘。后半段是我在纯工程角色里学不到的东西。
